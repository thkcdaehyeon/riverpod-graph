# 0004 — 위젯 의존성 트리는 정적 분석 + 한계 마커

날짜: 2026-05-10
상태: 채택

## 맥락

목표 #3 — "특정 위젯과 하위 위젯이 의존하는 provider/notifier를 한 눈에" 달성을 위해 두 길이 있다:

1. **정적 분석** — Dart 소스 AST를 보고 build 메서드 안 위젯 생성자 호출과 ref 호출을 따라간다. IDE 시점에 즉시 동작.
2. **런타임 introspection** — 실행 중 Flutter 앱에서 실제 위젯 트리와 ProviderContainer 상태를 읽어옴 (Flutter inspector 패턴). 정확하지만 앱 실행 필수.

런타임 경로는 정확하나 IDE 정적 도구로서 가치 절반 — 앱이 그 화면에 도달해야만 보인다. 코드 리뷰/리팩토링/온보딩에서 즉시 안 보임.

정적 분석은 본질적으로 한계가 있다:
- 조건부 children (`if`, `?:`)
- 반복 children (`map`, `for`, spread `...`)
- 콜백 children (`Builder(builder: ...)`, `ListView.builder`, `FutureBuilder`)
- 외부 패키지 위젯의 children (소스 접근 어려움/비효율)
- 라우팅 (`Navigator.push` 같은 동적 화면 전이)
- 동적 타입 (`Widget Function()` 변수)

## 결정

**정적 분석만 사용한다. 한계가 있는 위치는 명시 마커로 솔직하게 표시한다.**

- 자식 후보 추출: build 메서드 안 Widget(또는 하위 타입) 반환 모든 생성자/함수 호출을 후보로. 회수율 우선.
- 마커:
  - 🔀 조건부
  - 🔁 반복
  - 🎯 콜백
  - ⚙ Ref 확장 호출 (사용자가 펼침 토글로 본문 의존성 노출)
  - ↻ cycle (의존 그래프 순환)
- traversal 범위: 같은 pub package 내. 외부 패키지 위젯은 자기 자체 분석 없이 인자로 들어간 위젯만 따라감.
- depth: 기본 5, 토글 무한.

## 대안

1. **런타임 introspection 통합** — 거부. IDE 정적 분석 가치를 흐림. 앱 실행 의존. v3 검토 가능.
2. **표준 슬롯 인자만 자식으로** (`child:`, `children:`, `body:`, ...) — 거부. 정밀도 ↑이지만 누락 시 사용자 신뢰 ↓. 사용자가 마커보다 누락을 더 못 견딘다.
3. **분석 신뢰도 점수** (0~100점 confidence) — 거부. UX 복잡. 마커 시스템이 이미 정성적으로 같은 정보 전달.
4. **외부 패키지 위젯 본문 분석** — 거부. 패키지 마다 src 접근/캐시 다름. 첫 릴리스 비용 과다.

## 결과

- 위젯 dep view는 "정확한 런타임 답"이 아닌 "정적으로 가능한 최선"임을 사용자에게 명시 (Tool Window 안내 + README).
- 사용자 멘탈 모델이 "이 코드가 잠재적으로 의존하는 모든 provider"여야 정합. 거짓 완벽함 < 솔직한 한계.
- ProviderScope override 같은 "런타임 결정 사항"도 같은 이유로 v1 미반영 (ADR 별도 없음 — 본 결정의 자연 귀결).
